# DRI Task Manager

**Version 1.0.0**  
LangGenius  
February 2026

> **Note:**  
> このドキュメントは、エージェントやLLMがタスクを作成・管理する際に従うべきルールです。
> DRI（Directly Responsible Individual = 直接責任者）を適切に設定し、責任の所在を明確にするための
> 指針を提供します。人間にも有用ですが、主にAI支援ワークフローでの自動化と一貫性のために
> 最適化されています。

---

## 概要

DRIは、1つのタスクに対して1人の責任者を明確にする仕組みです。組織の成長に伴う「誰に聞けばいいかわからない」「決定が遅い」「責任の所在が曖昧」といった問題を解決します。

## 1. DRI定義と役割

### 1.1 DRIの基本原則

**DRI（Directly Responsible Individual）**
- 1つのタスクに対して、1人の責任者を明確にする
- DRIは最終決定権を持ち、結果に責任を負う
- 質問・報告・エスカレーションはDRIに一本化

### 1.2 役割の定義

| 役割 | 意味 | 人数 | 権限 |
|------|------|------|------|
| **DRI** | 最終決定権を持ち、結果に責任を負う | **1名のみ** | 決定権あり |
| **相談役** | アドバイス・レビューを行う | 複数可 | 決定権なし |
| **共有先** | 状況を把握しておく必要がある人 | 複数可 | アクション不要 |

❌ **不可:** DRIを複数人に設定する

```
タスク          DRI           期限
API設計        山田, 鈴木     02/15
```

✅ **正しい:** DRIは1人、もう1人は相談役にする

```
タスク          DRI    相談役    期限
API設計        山田    鈴木      02/15
```

---

❌ **不可:** チーム名やグループ名をDRIに設定する

```
タスク               DRI          期限
フロントエンド実装    開発チーム    03/01
```

✅ **正しい:** チームの中から1人の個人を特定する

```
タスク               DRI     相談役             期限
フロントエンド実装    伊藤    田中, 佐藤         03/01
```

## 2. 出力フォーマット

### 2.1 DRIマトリクス形式

タスクを作成・整理する際は、必ず以下のマトリクス形式で出力する：

```
タスク                        DRI   相談役          共有先        期限    状態
─────────────────────────────────────────────────────────────────────────────
リポジトリ構成決定              YAN   kodama, 天培   kodama        02/07   ✅完了
ベンダー権限設定                YAN   天培           kodama        02/10   🟡進行中
ブランチ運用ルール策定           YAN   kodama        天培, 橋本    02/14   ⚪未着手
```

### 2.2 状態の表記

| 記号 | 意味 | 使用場面 |
|------|------|----------|
| ⚪ | 未着手 | タスク作成時の初期状態 |
| 🟡 | 進行中 | 作業が開始された |
| 🔴 | ブロック中 | 何らかの理由で進められない（理由を併記） |
| ✅ | 完了 | タスクが完了した |

❌ **不可:** 状態を曖昧にする

```
タスク          DRI    期限    状態
API実装        山田    02/20   たぶん進行中
```

✅ **正しい:** 明確な状態記号を使う

```
タスク          DRI    期限    状態
API実装        山田    02/20   🟡進行中
```

---

❌ **不可:** ブロック中の理由を書かない

```
タスク          DRI    期限    状態
DB移行         鈴木    02/25   🔴ブロック中
```

✅ **正しい:** ブロック中の場合は理由を併記する

```
タスク          DRI    期限    状態
DB移行         鈴木    02/25   🔴ブロック中（本番環境のアクセス権限待ち）
```

## 3. タスク作成の流れ

### 3.1 対話型・段階的アプローチ

タスク作成は会話を通じて段階的に進める。一度に全部決めない。

```
ステップ1: タスクの洗い出し
  ユーザーと会話しながらタスクを特定する
  「過不足ないですか？」と確認する
  ↓
ステップ2: DRI・期限・状態を決める
  各タスクにDRIを1名設定し、期限と状態を確定する
  NotionのPosition情報を参考にDRIを提案する
  （相談役・共有先は空欄のまま出力してOK）
  ↓
ステップ3: 粒度の確認
  タスクが大きすぎる場合は親子タスクに分割する
  完了まで2週間以上の場合は分割を提案する
  ↓
ステップ4: 相談役・共有先を決める（後日でもOK）
  Notion・Slackのやり取り履歴を参考に提案する
  「後で決めましょう」でも進める
```

❌ **不可:** 一度に全ての情報を要求する

```
「タスク名、DRI、相談役、共有先、期限、状態を全て教えてください」
```

✅ **正しい:** 段階的に確認する

```
「まず、どのようなタスクがありますか？」
→ タスクリスト確認
→ 「過不足ないですか？」
→ 「では、各タスクのDRIを決めましょう」
→ DRI・期限・状態を確定
→ 「相談役は後で追加できますので、まずはこれで進めましょうか？」
```

---

### 3.2 DRIの提案方法

❌ **不可:** エージェントが勝手にDRIを決定する

```
「このタスクのDRIは山田さんにします」（ユーザーに確認なし）
```

✅ **正しい:** NotionのPosition情報を参考に提案し、ユーザーに確認する

```
「このタスクはAPI開発ですので、Positionが"Backend Engineer"の山田さんがDRIに
適しているかと思いますが、いかがでしょうか？」
```

---

### 3.3 相談役・共有先の扱い

❌ **不可:** 相談役が決まらないからタスク作成を止める

```
「相談役が決まっていないので、タスクを作成できません」
```

✅ **正しい:** 相談役・共有先は後から追加できることを伝える

```
タスク          DRI    相談役    共有先    期限    状態
API実装        山田              　        02/20   ⚪未着手

「相談役は後から追加できますので、まずはDRIと期限を確定して進めましょう」
```

## 4. 親子タスクの分割

### 4.1 分割が必要な目安

以下の場合、親子タスクへの分割を提案する：

- 完了まで2週間以上かかる
- 成果物が複数ある
- 複数の領域にまたがる

❌ **不可:** 大きすぎるタスクをそのまま作成する

```
タスク                DRI    期限    状態
新サービス開発         山田   06/30   ⚪未着手
```

✅ **正しい:** 親子タスクに分割する

```
親タスク                       DRI    期限    状態
──────────────────────────────────────────────────
新サービス開発                  山田   06/30   ⚪未着手

  └ 子タスク                   DRI    期限    状態
    ──────────────────────────────────────────────
    要件定義                   山田   03/15   ⚪未着手
    技術選定                   鈴木   03/31   ⚪未着手
    設計・実装                 田中   05/15   ⚪未着手
    テスト                    佐藤   06/15   ⚪未着手
    リリース準備               山田   06/30   ⚪未着手
```

---

### 4.2 親子タスクのルール

1. **親タスクにもDRIを設定する**（プロジェクト全体の完遂に責任を持つ）
2. **子タスクのDRIは親と別でもいい**（各子タスクに最適な人をDRIにする）
3. **親タスクの期限 ≧ 全子タスクの期限**
4. **親タスクの状態は子タスクから自動判定**

❌ **不可:** 親タスクの期限が子タスクより早い

```
親タスク              DRI    期限    状態
認証基盤刷新          中村   03/31   ⚪未着手

  └ 子タスク         DRI    期限    状態
    設計             伊藤   04/15   ⚪未着手  ← 親より遅い
```

✅ **正しい:** 親タスクの期限は全子タスクを包含する

```
親タスク              DRI    期限    状態
認証基盤刷新          中村   04/30   ⚪未着手

  └ 子タスク         DRI    期限    状態
    設計             伊藤   04/15   ⚪未着手
```

## 5. バリデーションルール

### 5.1 必須ルール（満たさなければ出力しない）

1. ✅ **DRIが1名だけ設定されている**
2. ✅ **DRIはNotionに登録された個人名**（チーム名やグループ名は不可）
3. ✅ **期限が設定されている**

❌ **不可:** 必須項目が欠けている

```
タスク          DRI    期限    状態
API実装                       ⚪未着手  ← DRIがない
DB設計         山田            ⚪未着手  ← 期限がない
```

✅ **正しい:** 全ての必須項目を含む

```
タスク          DRI    期限    状態
API実装        鈴木   02/20   ⚪未着手
DB設計         山田   02/25   ⚪未着手
```

---

### 5.2 警告ルール（出力はするが注意を促す）

1. ⚠️ **同一人物がDRIとして4つ以上のタスクに入っている** → 過負荷の恐れあり
2. ⚠️ **状態が🔴ブロック中なのに理由がない** → 理由の記入を促す
3. ⚠️ **タスクの完了見込みが2週間以上** → 子タスクへの分割を提案する

✅ **正しい:** 警告を伝える

```
タスク          DRI    期限    状態
API実装        山田   02/20   ⚪未着手
DB設計         山田   02/25   ⚪未着手
UI実装         山田   03/01   ⚪未着手
テスト         山田   03/05   ⚪未着手

⚠️ 注意: 山田さんがDRIとして4つのタスクを持っています。
過負荷になっていないか確認することをお勧めします。
```

## 6. エージェントの振る舞い

### 6.1 やること ✅

1. **タスクの洗い出しではユーザーに「過不足ないですか？」と確認する**
2. **DRIの設定ではNotionのPosition情報を参考に提案する**
3. **大きすぎるタスクには分割を提案する**
4. **相談役・共有先は「後で決めましょう」でも進める**

### 6.2 やらないこと ❌

1. **一度に全部決めようとしない**（段階的に進める）
2. **DRIをエージェントが勝手に決めない**（必ずユーザーに確認する）
3. **相談役がいないからといってタスク作成を止めない**（後から追加できる）

## 7. 具体例とアンチパターン

### 7.1 DRIの判断基準

DRIを誰にすべきかわからない場合、以下の順で判断する：

1. **そのタスクを一番よく知っている人は誰か**
2. **その人は決定を下せる立場か**
3. **その人は今の業務量的に引き受けられるか**（同時DRI上限3つ推奨）

❌ **不可:** 役職だけで判断する

```
「マネージャーなので、全てのタスクのDRIは部長にします」
```

✅ **正しい:** タスク内容と専門性で判断する

```
タスク                  DRI     期限    状態
技術選定                鈴木    02/15   ⚪未着手  ← 技術に詳しい人
予算承認                部長    02/10   ⚪未着手  ← 承認権限を持つ人
実装                    田中    03/01   ⚪未着手  ← 実装担当者
```

---

### 7.2 DRIが決定を覆された場合

❌ **不可:** DRIの決定を上位者が覆すが、DRIは変更しない

```
「山田さん（DRI）の決定を部長が覆しましたが、DRIは山田さんのままです」
```

✅ **正しい:** 決定を覆した人が新しいDRIになる

```
「部長が山田さん（元DRI）の決定を覆しました。
新しいDRIは部長になります。決定権を取るなら、責任も取ります。」

タスク          DRI    期限    状態
技術選定        部長   02/15   🟡進行中  ← 元DRIは山田
```

---

### 7.3 メンバー情報の参照

NotionのメンバーページからLangGeniusのメンバーを参照する。

**利用可能なフィールド：**
- **Name** - DRI・相談役・共有先のアサインに使用
- **Position** - タスク領域に適した人の判断に使用

❌ **不可:** Position以外の情報（経験年数、スキルレベル等）を勝手に推測する

```
「山田さんは経験10年なので、このタスクに適しています」（経験年数は不明）
```

✅ **正しい:** Name と Position のみを使用する

```
「このタスクはAPI開発ですので、Positionが"Backend Engineer"の
山田さんがDRIに適しているかと思いますが、いかがでしょうか？」
```

---

### 7.4 相談役・共有先のアサイン

❌ **不可:** タスク作成時に相談役・共有先を必須にする

```
「相談役が決まるまでタスクを作成できません」
```

✅ **正しい:** タスク作成時はDRI・期限・状態のみ確定し、相談役・共有先は後から決定する

```
ステップ1（タスク作成時）:
タスク          DRI    相談役    共有先    期限    状態
API実装        山田                        02/20   ⚪未着手

ステップ2（後日、相談役・共有先を追加）:
タスク          DRI    相談役    共有先      期限    状態
API実装        山田    鈴木      田中, 佐藤  02/20   🟡進行中
```

## まとめ

DRI Task Manager は、タスクの責任者を明確にすることで、意思決定を迅速化し、
組織の成長に伴う混乱を防ぐためのスキルです。

**重要なポイント：**
1. **DRIは必ず1人**
2. **段階的にタスクを作成**（一度に全部決めない）
3. **大きすぎるタスクは分割する**
4. **相談役・共有先は後から追加できる**

エージェントは常にユーザーと対話しながら、適切なDRIを提案し、
タスク管理をサポートします。
